# pyamtrack: bug hunt, documentation review, architecture assessment and development plan

Date: 2026-08-06
Scope: `libamtrack/pyamtrack` @ `b9d413b`, `libamtrack/libamtrack.github.io` @ `39558bb`,
cross-checked against `libamtrack/library` @ `master` and nanobind v2.10.2.

Every claim below was verified against source. Where a claim depends on library
internals (libamtrack data tables, nanobind exception hierarchy, nanobind's ndarray
caster lifetime rules) the verifying file and line are cited.

---

## 0. Executive summary

The binding layer is small (~4 kLOC) and the physics kernels are upstream, so the
defect surface is concentrated in three places:

1. **The boundary with libamtrack is unguarded.** libamtrack signals errors with
   `assert()`, sentinel returns and `printf` — never exceptions. pyamtrack forwards
   user input straight through. The result is either a silently wrong number
   (release builds) or a `SIGABRT` that kills the interpreter (asserts enabled).
2. **The four-extension-module layout** forces `stopping` to reach into `materials`
   through the *Python* interpreter on every call, and gives each `.so` its own copy
   of libamtrack's mutable `AT_Material_Data`.
3. **The published documentation contradicts the code** in ways that produce wrong
   physics: the website lists the wrong material IDs, and every keyword-argument
   example on the types page uses parameter names that do not exist.

Roughly 30 concrete defects follow, then a phased plan.

## 1. Physics / data correctness

### P1 — Neutron PDG code is wrong (HIGH)

`src/particles/construct_utils.h:260`

```cpp
inline std::map<std::string, long long> pdg_for_nonions = {
  {"neutron", 2122},   // <-- 2112
  {"electron", 11}
};
```

`2112` is the neutron; `2122` is a Δ⁺ baryon. Consequences:

- `particles.from_string("neutron").pdg == 2122`
- `particles.from_pdg(2112).pdg == 2122` — the round-trip does not close.

No test asserts `.pdg` for non-ions (`tests/test_particles.py:84-94` checks only
`element_name`), which is why it survived. Noted in passing in issue #200 but not
tracked or fixed.

### P2 — Invalid material IDs silently produce garbage, or abort the process (HIGH)

`src/stopping/electron_range.cpp:70` passes `material` through `process_material`,
which accepts *any* integer without range-checking it against libamtrack's
`material_no` table (valid: 1..24, `AT_DataMaterial.h:42-68`).

Downstream, `AT_get_material_data` (`src/AT_DataMaterial.c`) zero-fills all outputs
for an unknown id and returns normally. Then `AT_max_electron_range_m`
(`src/AT_ElectronRange.c`):

```c
assert( average_A > 0);
assert( average_Z > 0);
...
assert ( material_density_g_cm3 > 0);
max_electron_range_m *= 1e-2 / material_density_g_cm3;
```

- Release build (`NDEBUG`, which is what pyamtrack ships): asserts vanish, division
  by zero → `inf`. No error, no warning.
- Any build with asserts enabled: `SIGABRT`. A C `assert` firing under a Python
  extension terminates the interpreter — no exception, no traceback.

This is reachable today and is exercised by the test suite:
`tests/test_stopping.py:43` passes `material=0` and the test passes.
`test_invalid_id` — the one test that would catch it — is `@pytest.mark.skip`
(`tests/test_stopping.py:101`).

### P3 — Invalid model IDs return a plausible wrong number (HIGH)

`process_model` (`src/stopping/electron_range.cpp:40`) validates model *names* but
accepts any *integer* unchecked. `AT_max_electron_range_m`'s dispatch ends in:

```c
default:
  max_electron_range_g_cm2  =  E_MeV_u; /* ER model Test, echoing E_MeV_u */
```

So `electron_range(100.0, model=999)` returns `1.0` — a number that looks like a
range in metres and is not one. Silent physics corruption.

### P4 — `Particle.id` is wrong for Z ≥ 86, and mis-documented for everything (MEDIUM-HIGH)

`src/particles/particles.cpp:155` sets `p.id = it + 1` where `it` is the row index in
`AT_Particle_Data`. libamtrack's Z column (`include/AT_DataParticle.h:76-85`) is
**not contiguous** — Z=85 (astatine) and Z=87 (francium) are absent:

```
..., 81, 82, 83, 84, 86, 88, 89, 90, 91, 92, 93, 94, 95, 96, 97, 98
```

| element | `Particle.id` | actual Z |
|---|---|---|
| Rn | 85 | 86 |
| Ra | 86 | 88 |
| U  | 90 | 92 |
| Cf | 96 | 98 |

12 of 96 elements are affected. The docstring (`src/particles/particles.h:56`,
`src/particles/particles_bindings.cpp:27`) says `id` is the "row index in
AT_Particle_Data" — it is the row index **+ 1**. So `id` is neither Z nor the row
index, and for the other 84 elements it is simply a duplicate of `Z`.

### P5 — `Particle` cannot address libamtrack's particle table (HIGH — blocks porting)

libamtrack identifies particles by `particle_no = 1000·Z + A`
(`AT_particle_no_from_Z_and_A_single`, `src/AT_DataParticle.c`), and *every*
remaining function to be ported takes it: `AT_Stopping_Power`, the RDD family, the
Katz model, `AT_CSDA_range`, the Bortfeld/Wilkens models. `Particle` exposes
`id`, `pdg`, `Z`, `A`, `atomic_weight` — but no `particle_no`.

This blocks issues #62, #94, #95, #197 and should be fixed before, not during, the
next porting push. Note `AT_particle_no_from_Z_and_A_single` also asserts
`1 <= Z <= 118 && 1 <= A <= 300`, so the conversion needs its own guard (see P2).

### P6 — Special-particle names are case-sensitive; `"n"` returns nitrogen (MEDIUM)

`from_string` (`src/particles/particles.cpp:74`) compares `name == "neutron"`
exactly, while element lookup in `create_ion` is case-insensitive
(`to_lower_case` on both sides, line 126). So:

- `from_string("proton")` → proton; `from_string("Proton")` → `ValueError`.
- `from_string("n")` → **Nitrogen**, because the acronym match is case-folded.
- `from_string("p")` → **Phosphorus**.

### P7 — `create_particle` is a stub with silent failure modes (MEDIUM)

`src/particles/particles.cpp:91`

```cpp
Particle create_particle(const std::string& name) {
  Particle p = Particle();
  p.element_name = name;
  p.element_acronym = name[0];        // char -> std::string; "neutron" -> "n" by luck
  p.pdg = pdg_for_nonions[name];      // map::operator[] inserts 0 for unknown keys
  return p;
}
```

`id` stays `-1` and `atomic_weight` stays `0.0`; the neutron's mass is simply absent.
The `operator[]` on a non-const global map is also a mutation of shared state (see B11).

### P8 — Default-isotope table has three wrong entries (LOW)

`src/particles/construct_utils.h`, `most_popular_iso_A`:

| element | table | most abundant |
|---|---|---|
| Sn | 119 | 120 (32.6 %; ¹¹⁹Sn is 8.6 %) |
| Mo | 96  | 98 (24.4 %; ⁹⁶Mo is 16.7 %) |
| Dy | 163 | 164 (28.3 %; ¹⁶³Dy is 24.9 %) |

Verified as *correct*: both tables contain exactly the 96 elements libamtrack ships,
with no missing or extra keys, so the `most_popular_iso_A[acronym]` /
`isotope_A_range` lookups cannot currently silently yield `A = 0`. Nothing tests this
invariant, though.

### P9 — Two electron-range models are unreachable (LOW)

`AT_ERModels` (`include/AT_ElectronRange.h`) defines `ER_AM_RadDiff = 9` and
`ER_Kiefer = 10`; `STOPPING_MODELS` (`src/stopping/electron_range.h:22`) stops at 8.
Note `AT_max_electron_range_m` treats `ER_AM_RadDiff` specially (it skips the density
rescaling), so exposing it needs more than a map entry.

### P10 — PET isotopes are not representable (LOW, domain gap)

`isotope_A_range` admits only stable isotopes: `C {12,14}`, `N {14,15}`, `O {16,18}`.
For a particle-therapy library the β⁺ emitters ¹¹C, ¹³N and ¹⁵O (in-beam PET range
verification) are arguably the most interesting non-stable isotopes and cannot be
constructed at all.

## 2. Binding-layer correctness

### B1 — Exception types are silently downgraded to `RuntimeError` (HIGH)

Verified in nanobind v2.10.2, `include/nanobind/nb_error.h:98`:
`builtin_exception : public std::runtime_error` — so `nb::value_error` and
`nb::type_error` are caught by `catch (const std::exception&)`.
(`nb::cast_error` is `std::bad_cast`, line 90, so it is *not* caught by a
`catch (const std::runtime_error&)`.)

Two places throw a typed nanobind exception inside a `try` whose handler re-wraps it:

**`src/materials/materials.h:46-73`**

```cpp
try {
  ...
  if (!nb::isinstance(material, MaterialType)) {
    throw nb::type_error("Material argument must be an integer or a "
                         "pyamtrack.materials.Material object");   // :56
  }
  ...
} catch (const nb::python_error& e) { throw; }
  catch (const nb::cast_error& e)   { ... }
  catch (const std::exception& e)   {                              // :67  <-- catches :56
    throw std::runtime_error("An error occurred while processing the "
                             "Material object: " + std::string(e.what()));
  }
```

Python sees `RuntimeError`, not `TypeError`. The website documents `TypeError`
(`docs/python/API/stopping/electron_range.md:138`) and the test suite asserts
`RuntimeError` (`tests/test_stopping.py:89-98`) — docs and tests already contradict
each other, and the test encodes the bug.

**`src/wrapper/single_argument.h:57-91`** — the same shape. The
`nb::value_error("NDArray must be C-contiguous…")` at line 58 is thrown inside the
`try` and re-wrapped at line 89 as `std::runtime_error`. The function's own docstring
(line 24) and the website (`docs/python/types.md` §5.4) both promise `ValueError`.

### B2 — Reachable memory leaks on the error path (MEDIUM)

**`src/wrapper/multi_argument.h:106`**

```cpp
double* results = new double[input_length];
try { ... }
catch (const nb::cast_error& e) { throw nb::type_error(...); }      // no delete[]
catch (const std::exception& e) { throw std::runtime_error(...); }  // no delete[]
```

**`src/wrapper/cartesian_product.h:150`** — `new double[output_size]`, then
`assign_val` (line 159) can `throw nb::type_error` at lines 165, 168, 174 and 182,
all before the owning `nb::capsule` is created at line 188. Reachable from Python
because `parse_input` does not type-check list elements
(`cartesian_product.h:83`: `for (auto item : list) tmp.push_back(nb::cast(item));`):

```python
electron_range([1.0, "x"], 1, 7, cartesian_product=True)   # leaks output_size doubles
```

The fix in both cases is `std::unique_ptr<double[]>` + `.release()` into the capsule.

*Ruled out:* there is **no** use-after-free from nanobind's implicit dtype
conversion. `nb_ndarray.cpp:715-733` recurses into `ndarray_import`, which sets
`result->self = src; Py_INCREF(src)`, so the `ndarray` value keeps the converted
temporary alive independently of the cleanup list.

### B3 — O(N²·K) work in the vectorized path (HIGH — performance)

`src/wrapper/multi_argument.h:108-121`

```cpp
for (size_t i = 0; i < input_length; i++) {          // N elements
  for (auto& argument : arguments) {                 // K arguments
    ...
    auto array = nb::cast<nb::ndarray<const double, nb::shape<-1>>>(argument);  // :118
    arguments_vector.emplace_back(array(i));
  }
}
```

The cast is re-done for **every element**. For any argument whose dtype is not
`float64`, nanobind's caster performs a full `astype` conversion each time
(`nb_ndarray.cpp:715-733`) — so an int64 material array of length N causes N full
N-element conversions: **O(N²·K) time and O(N) transient allocations of O(N) bytes
each**. Even for `float64` inputs it is N·K caster round-trips plus refcount churn
where a single hoisted `const double*` would do.

The tests never expose this: the longest array in `test_arrays_with_mixed_dtypes` is
3 elements. There is no benchmark anywhere in the repo.

Related: `prepare_array_argument` (`multi_argument.h:19`) materialises a full
N-element `float64` array for *each* scalar argument purely to broadcast it, and
loses the int/float distinction while doing so (everything becomes `double` in the
`std::variant`).

### B4 — Cartesian output shape contradicts the published contract (MEDIUM)

`cartesian_product.h:44-46` pushes **all** dimensions of every array input into
`output_shape`. So a `(2,2)` energy array × 3 materials × 2 models yields
`(2,2,3,2)`. The website (`docs/python/types.md:194`) states the result is `(4,3,2)`
and that "input ndarrays are flattened to 1-D". The *shape* is not flattened.
`tests/test_cartesian_product.py` and `examples/example.ipynb`
(`res[0, 0, 1, 1]` on a `(2,2)` input) both confirm the code's behaviour — only the
docs are wrong, but the actual contract is documented nowhere.

### B5 — `cartesian_product=True` changes the scalar return type (LOW-MEDIUM)

With all-scalar arguments, `output_shape` is empty, so the result is a **0-d
ndarray**; the same call with `cartesian_product=False` returns a Python `float`.
`docs/python/types.md` §3.1 promises a float unconditionally.
`tests/test_cartesian_product.py:171-179` asserts the 0-d behaviour.

### B6 — Empty inputs discard shape in cartesian mode (LOW)

`cartesian_product.h:135` returns `nb::ndarray<double, nb::numpy>(nullptr, {0})`
regardless of the other arguments' dimensions, and constructs it from a `nullptr`
data pointer with no owner capsule.

### B7 — `nb::cast_error` escapes with a useless message (LOW)

`multi_argument.h:97` is *outside* the `try` that begins at line 107. Because
`nb::cast_error` is `std::bad_cast`, an escaping failure surfaces as
`RuntimeError: std::bad_cast`.

### B8 — Read-only arrays rejected in cartesian mode only (LOW)

`process_array<T>` (`cartesian_product.h:28`) casts to non-const `nb::ndarray<T>`,
which requires a writable buffer. `arr.flags.writeable = False` arrays and
`np.frombuffer` results fail in cartesian mode but work element-wise.
Should be `nb::ndarray<const T>`.

### B9 — NumPy scalar types are inconsistently accepted (LOW-MEDIUM)

`np.float64` subclasses Python `float`, so `PyFloat_Check` accepts it. `np.int64`,
`np.int32`, `np.float32` do not subclass anything and are neither `nb::int_`,
`nb::float_`, nor `nb::ndarray` — they raise `TypeError`.
`docs/python/types.md:16` lists `np.float32` as an accepted scalar. It is not.

### B10 — The GIL is held for the entire computation (MEDIUM)

No `nb::call_guard<nb::gil_scoped_release>` anywhere. A million-element
`electron_range` blocks the whole interpreter. This is also the first blocker for
issue #116 (free-threaded wheels), together with B11.

### B11 — Mutable global state in headers (MEDIUM)

`most_popular_iso_A` and `isotope_A_range` (`construct_utils.h:48, 155`) are
non-`const` `inline std::map`s accessed with `operator[]` — a mutating operation on
shared global state. Safe only because the GIL currently serialises everything;
a data race the moment B10 or free-threading lands. Both should be `const` with
`.find()` lookups, and moved out of the header (see C5 / issue #200).

### B12 — `parse_isotope` control flow (LOW)

`construct_utils.cpp:20-56`: `int A;` is declared uninitialized and the function has
a fall-off-the-end path (lines 53-56). Provably unreachable today, but it is
`-Wreturn-type` bait and will become a real bug the moment the branches change.

### B13 — No overflow guard before allocation (LOW)

`cartesian_product.h:145-150`: `output_size *= shape[i]` then `new double[output_size]`
with no `size_t` overflow check and no size cap. Not exploitable on 64-bit with real
arrays, but it is one line to guard.

## 3. Architecture

### A1 — Four extension modules is the root problem (HIGH)

`CMakeLists.txt:157` builds `converters`, `stopping`, `materials` and `particles` as
four independent `NB_MODULE`s, each a separate `.so`, each linking `amtrack`, each
with its own nanobind type registry. Consequences:

- **`stopping` cannot see `materials`' C++ `Material` type.** That is the sole reason
  `process_material` (`materials.h:46`) does
  `nb::module_::import_("pyamtrack.materials")` → `attr("Material")` → `isinstance` →
  `attr("id")` — a Python import and three attribute lookups **per call**, and per
  *element* when a list of `Material` objects is passed. With a single module this
  is `nb::cast<Material>(obj).id`.
- **Each `.so` gets its own copy of `AT_Material_Data`.** libamtrack declares it
  `static AT_table_of_material_data_struct AT_Material_Data = {...}` in the *header*
  (`include/AT_DataMaterial.h:166`), and several of its fields are **mutable**
  (`ready[]`, `density_g_cm3[]`, `I_eV[]`, `average_A[]`, `average_Z[]`). The moment
  pyamtrack exposes `User_Defined_Material` (id 0) or anything that calls
  `AT_set_user_material_*`, the mutation will be invisible to the other three
  modules. Latent today; a genuinely nasty bug when it lands.
- 4× nanobind runtime, 4× `amtrack` link, larger wheels, slower import.
- `_core` is vestigial: `src/main.cpp` sets only `__version__`, and
  `src/pyamtrack/__init__.py` does not even import it. Its `__version__` is dead
  code — the real one comes from `_version.py`.

**Fix:** one `_core` extension, with `nb::module_::def_submodule` for
`converters` / `stopping` / `materials` / `particles`, and thin Python shim modules
(`pyamtrack/materials.py` → `from pyamtrack._core.materials import *`) to preserve
`import pyamtrack.materials`. This is a prerequisite for A2 and makes `_core`
meaningful.

### A2 — There is no validation layer, and libamtrack requires one (HIGH)

libamtrack's error contract is `assert` / sentinel / `printf`:

| libamtrack behaviour | example |
|---|---|
| `assert()` on bad input | `AT_max_electron_range_m`, `AT_particle_no_from_Z_and_A_single` |
| zero-fill and return | `AT_get_material_data` for unknown `material_no` |
| return `-1` and `printf` to stdout | `AT_Z_from_particle_no_single` |
| silent fallthrough | `AT_max_electron_range_m` `default:` branch |

None of these can cross a Python boundary safely. pyamtrack must own the checks —
this is not upstream's job, it is the binding's job. Recommend `src/validation/`
with `check_material_no`, `check_er_model`, `check_Z_A`, `check_energy_domain`,
each raising `nb::value_error` with a message naming the offending argument, applied
before every AT call. P2, P3 and P5 all collapse into this one piece of work.

### A3 — Builds are not reproducible (HIGH)

`CMakeLists.txt:126-130`

```cmake
FetchContent_Declare(
  libamtrack
  GIT_REPOSITORY https://github.com/libamtrack/library.git
  GIT_TAG master)
```

Every wheel — including every *released* wheel — is built against whatever `master`
was at build time. Two builds of the same pyamtrack tag can contain different
physics. An upstream regression ships silently, and a released wheel cannot be
reproduced or audited. Pin a commit SHA (`GIT_TAG <sha>` + `GIT_SHALLOW OFF`), and
let Dependabot/Renovate open the bump PRs. This also makes the weekly scheduled CI
runs meaningful: they'd be testing `master` against a pinned baseline instead of
testing nothing in particular.

### A4 — No type information (MEDIUM)

No `py.typed`, no `.pyi`. Every signature is `nb::object` in / `nb::object` out, so
even runtime introspection gives users nothing. nanobind ships
`python -m nanobind.stubgen`; generating stubs in CI and shipping them (plus a
`py.typed` marker) is a few lines and a large DX win for a scientific package.

### A5 — The wrapper layer is the thing to fix before porting more functions (HIGH)

`src/wrapper/` conflates two orthogonal axes — arity (1 vs N) × broadcast semantics
(zip vs cartesian) — into three hand-written files with duplicated and *divergent*
dtype/contiguity/shape logic:

| behaviour | `single_argument` | `multi_argument` | `cartesian_product` |
|---|---|---|---|
| C-contiguity checked | yes | **no** | yes |
| ndim allowed | any | **1 only** | any |
| all-scalar return | `float` | `float` | **0-d array** |
| list return | Python `list` | ndarray | ndarray |
| int dtype handling | cast to double | cast per element (B3) | `long long` branch |
| leak-safe | yes | **no** (B2) | **no** (B2) |

Issues #62 and #188 propose porting a dozen more functions on top of this. Every one
of them would inherit all six inconsistencies. Rewrite first: one generic
`vectorize(func, args, mode)` over `nb::ndarray`, with a single dtype-normalisation
step, explicit broadcasting, `unique_ptr` output buffers, and one documented set of
return-type rules.

### A6 — Test suite validates shapes, not physics (HIGH)

Every assertion in `tests/` is a shape check, a sign check, a monotonicity check or a
"models agree within 25×" check. `tests/test_converters.py` is two assertions in
total (`beta < 0.5`, `energy > 80`). **Nothing in the suite would catch a numerically
wrong kernel, a wrong material-ID mapping, a wrong PDG constant, or a bad isotope
default.** That is exactly why P1 and the doc bugs in §4 survived.

Needed: golden-value tests with tolerances against ICRU/NIST/analytic references —
e.g. `beta_from_energy(150) ≈ 0.5069` from `β = √(1 − (1 + E/931.494)⁻²)`,
`electron_range` at known energies per model, `Material(7).density_g_cm3 == 1.20479e-3`,
`from_string("neutron").pdg == 2112`, and a round-trip property test
`from_pdg(x.pdg) == x` over all 96 elements.

### A7 — Non-deterministic tests (MEDIUM)

`tests/test_cartesian_product.py` uses bare `np.random.uniform` / `np.random.randint`
with no seed, then draws 100 random probe coordinates per parametrisation. A failure
is not reproducible from the log. Use `np.random.default_rng(seed)` — or better,
Hypothesis with a fixed profile.

### A8 — CI gaps (HIGH in aggregate)

- **Windows is not in the PR gate.** `main.yml` runs Linux → macOS only;
  `windows.yml` fires on push-to-master, cron and manual dispatch. A PR that breaks
  the Windows build merges green. `docs/tests.md` documents this as deliberate, but
  Windows is the platform with the most build-specific code (vcpkg GSL, DLL
  preloading in `__init__.py`, `x64-windows` hard-coded triplet in `CMakeLists.txt:86`).
- **macOS is gated on Linux succeeding** (`main.yml:26-27`), serialising feedback and
  hiding macOS-only breakage whenever Linux is red.
- **pre-commit is configured but never runs in CI** — and it shows. Merged into
  master right now: 4 files with no trailing newline (`construct_utils.h`,
  `ion.cpp`, `ions.h`, `particles.cpp`) and 13 lines with trailing whitespace, all
  from PR #195. `end-of-file-fixer` and `trailing-whitespace` are both configured.
- No coverage, no `ruff`, no `mypy`, no C++ `-Wall -Wextra -Werror`, and **no
  ASan/UBSan job** — which is precisely what would catch B2 and B13.
- **The sdist is built and `twine check`ed but never installed or tested**
  (`wheels.yml:26-43`). Combined with A3, an sdist install requires network access to
  GitHub at build time — worth an explicit test job.
- `pull-requests: write` is granted to build-only workflows that never write.

### A9 — Repo hygiene (MEDIUM)

No `CONTRIBUTING.md` (issue #19 asks for exactly this), `CHANGELOG.md`,
`SECURITY.md`, issue templates or PR template. `README.md:11` and the website both
still advertise "last stable release **0.14.0**, released **2022-10-03**".

### A10 — Build configuration nits

- `find_package(Python 3.8 ...)` (`CMakeLists.txt:52`) vs `requires-python = ">=3.9"`.
- `file(GLOB SOURCES src/${TARGET}/*.cpp)` (`:161`) — new files don't trigger a
  reconfigure. Use explicit lists or `CONFIGURE_DEPENDS`.
- `set(BUILD_SHARED_LIBS ON CACHE INTERNAL ...)` (`:137`) forces shared libs globally.
- `set(CMAKE_SHARED_LINKER_FLAGS "... -undefined dynamic_lookup")` on APPLE (`:150`)
  is applied **globally**, so it also covers `libamtrack` itself — hiding genuine
  undefined symbols until runtime. `nanobind_add_module` already handles this
  per-target; the global flag should go.
- `[tool.setuptools.packages.find]` (`pyproject.toml:50`) is dead — the backend is
  scikit-build-core.
- No minimum numpy pin (issue #81); `dependencies = ["numpy"]`. nanobind's ndarray
  path needs a reasonably modern numpy.
- Stable-ABI wheels (issue #82): `nanobind_add_module(... STABLE_ABI)` collapses
  cp312/313/314 into one wheel per platform — 18 wheels per release today.

## 4. Documentation

### Website (`libamtrack.github.io`)

**D1 — `docs/python/API/materials.md` publishes wrong material IDs (HIGHEST doc severity).**

Verified against `AT_DataMaterial.h:42-68`:
`Water_Liquid=1, Aluminum_Oxide=2, Aluminum=3, PMMA=4, Alanine=5, LiF=6, Air=7,
Silicon=8, Copper=9, Tungsten=10, … Lead=24`.

The published table (`materials.md:84-89`) and code comments (`:50-52`) say:

| published | actual |
|---|---|
| Air = 2 | Air = **7** |
| PMMA = 3 | PMMA = **4** |
| Aluminum = 4 | Aluminum = **3** |
| Air density 0.001225 | **1.20479e-03** |

A user who writes `material=2` believing it is air silently computes in aluminium

structural blockers (single module, validation layer, wrapper rewrite) *before* the
next porting push, so the new functions don't inherit today's defects.
